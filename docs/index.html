Strip 02 · how it holds

Give an agent the SDK and it can send any order. Pilot makes it wait for clearance.

Checked twice, sent once

plan_order runs the SDK's own previews against your policy and hands back a one-shot plan_id that expires in 60 s by default. place_order re-checks your policy, re-runs the liquidation and margin previews on live state and re-derives the limit price from the live book before it sends.

Limits no pilot tool can edit

They live in a file no pilot tool writes; policy only reads it. They carry over between sessions, and the daily cap counts across restarts.

~/.pilot/policy.json · the defaults "maxNotionalUsd": 25, "minLiquidationDistancePct": 15, "allowedMarkets": ["BTC", "ETH", "SOL"], "dailyOrderCap": 20, "maxSlippagePct": 1, "planTtlSec": 60

Closing is never blocked by your limits

close_position closes from the live on-chain size and your limits never stop it, not even an invalid policy file. When it cannot close (an empty book, the signer lock held elsewhere) it says why.

Every plan, refusal and transaction lands in an append-only journal. journal --card turns yours into a receipt to share:

Is it real?
What was staged?

Are these real orders?
Yes, on the Somnia testnet that dreamDEX's docs call Hideki (chain id 50383). Every transaction in DEMO.md was re-read from the RPC after the run, and each order and close hash links to its fill on dreamDEX's Hideki markets explorer (brackets and cancels are checked by the RPC only). Testnet only, with a burner key.
Which agents can use it?
Tested with Claude Code and Codex CLI over stdio; other MCP clients should work. Claude Code (Anthropic) opened 7 of the 9 recorded orders and Codex CLI (OpenAI) the other 2; MCP Inspector made read-only calls. Pilot has 9 tools: markets, account, plan_order, place_order, close_position, bracket, cancel_all, policy, journal.
Can the agent change its own limits?
Not through pilot: no pilot tool writes the policy file. Claude Code and Codex CLI also have shell and file tools that could read the key or edit that file, so the README's Getting Started section starts Claude Code with no built-in tools and Codex in a read-only sandbox (which still leaves it a shell), each checked with a throwaway key. Keep the burner small.
What happens when an order breaks a limit?
Nothing is sent. The refusal names the rule and a next safe action ("reduce size to at most 0.00031 BTC", "pick one of BTC, ETH, SOL"), says so when no order fits, and goes into the journal.
What was scripted or staged?
The prompts were written for the runs, and some refusals are scripted probes, such as a made-up plan id. One exchange refusal is race injected. The liquidation rule was shown under a test policy that lifts the cap to $1000, plans only. Later live runs are kept out of the DEMO.md counts. The Codex run in the hero was recorded on commit 0d18cec; since 5c81bcb pilot values a short at the top bid, so the same order would now read about $40.51.
Can it always get me out?
close_position is never blocked by your limits, even by an invalid policy file. It can still stop, for example on an empty book or when another pilot server holds the signer lock, and it says why.
Can I try it without a key?
Yes. Reads work keyless when PILOT_ACCOUNT names a public address; the README's Getting Started section uses the demo burner, and its second call (a $60 SOL plan) is refused by the default $25 cap with nothing sent.
